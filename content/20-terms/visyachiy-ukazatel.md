**Висячий указатель (dangling pointer) — [[20-terms/ukazatel|указатель]], который
хранит адрес уже несуществующего объекта.** Сам указатель жив, объекта нет.
Чтение или запись через такой указатель — [[20-terms/neopredelyonnoe-povedenie|Неопределённое поведение]].

## Зачем нужно

Указатель и объект живут независимо. Компилятор не следит за тем, чтобы
объект прожил не меньше указателя на него, — это обязанность программиста.
Ошибка не видна при компиляции и часто не видна при запуске: старые байты
какое-то время остаются на месте, и программа «работает».

## Как работает

Указатель провисает, когда **область действия объекта заканчивается раньше,
чем область действия указателя** (см. [[20-terms/oblast-deystviya|Область действия]]).

С автоматической переменной — на выходе из блока:

```cpp
int main() {
  int* p = nullptr;
  {
    int x = 0;
    p = &x;
  }  // x уничтожена, p указывает в никуда
  return *p;  // UB
}
```

С [[20-terms/dinamicheskaya-pamyat|динамической памятью]] — после `delete`. Обращение к
объекту после удаления называется **use after free**:

```cpp
int* p = new int(5);
delete p;
return *p;  // UB: use after free
```

Средство против второго случая на лекции сформулировано коротко: не обращаться
к объекту после `delete`.

## Тонкости

> [!info] Не из лекции
> Оба случая ловит AddressSanitizer: сборка `g++ -g -fsanitize=address`
> на первом примере печатает `ERROR: AddressSanitizer: stack-use-after-scope`,
> на втором — `heap-use-after-free` (GCC 16.2). См. [[20-terms/kompilyaciya-i-sborka|Компиляция и сборка]].

## Частые ошибки

- Сохранить адрес переменной из внутреннего блока или из функции и
  пользоваться им снаружи.
- Вызвать `delete` и продолжать пользоваться тем же указателем.
- Удалить объект через один указатель, забыв, что на него смотрит второй.
- Делать вывод «UB нет» из того, что программа напечатала правильное число.
